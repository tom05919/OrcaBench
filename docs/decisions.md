# Decision log

This log records protocol choices separately from experimental findings. A
decision may be revised when GPU evidence warrants it; revisions must retain the
old entry and explain the effect on comparability.

| Date | Decision | Basis and consequence |
|---|---|---|
| 2026-09-25 | Use `CerealAndBowl` as the first feasibility candidate. | It has an automatic physical predicate and a 4,350-step horizon. Qualification remains pending; selecting it is not a claim that it tests orchestration. |
| 2026-09-25 | Score cereal/counter contact, bowl/counter contact, and a closed cabinet. | This is exactly the pinned upstream `_check_success`. The upstream phrase “next to the milk” is not enforced, so the benchmark goal omits that relation. |
| 2026-09-25 | Expose three RGB views, listed proprioception, skill/history state, and budgets. | Object state, reward, success, predicates, subtask labels, and evaluator advice stay private. Current-frame access is the development default. |
| 2026-09-25 | Use six high-level operations and agent-selected intervals of 1–100 steps. | The runner owns synchronous physics and queue semantics. Switch, retry, and interrupt discard queued actions; only `continue` preserves them. |
| 2026-09-26 | Replace the six-operation skill interface with free-form `run_policy(prompt?, steps)` and `complete`. | The orchestrator may prompt the VLA as it sees fit. Prompts are nonblank, limited to 512 characters, and forwarded verbatim. Supplying any prompt, including the active text, discards pending actions and invokes the policy reset hook; omitting it continues the instruction and queue. The pinned backends have no recurrent instruction state. Physics already pauses at model boundaries, so no standalone interrupt is needed. Task-config and model-observation schemas advance to version 2. This supersedes the September 25 interface and changes the evaluation contract. |
| 2026-09-26 | Treat the four declared strings as reference qualification prompts, not an allowlist. | Their cards report exact-prompt performance under declared entry conditions. Arbitrary and dynamic prompts are permitted but remain unverified until GPU evidence exists. Existing qualification evidence retains the `skill` and `skill_conditions` field names for continuity. |
| 2026-09-25 | Require a correct completion declaration for primary success. | Physical completion without declaration and a false declaration are failures. Physical completion is retained as a diagnostic. |
| 2026-09-25 | Start with the official GR00T N1.5 checkpoint and reserve official π0.5 as fallback. | The backends are never mixed in a comparison. π0.5 begins only after a completed GR00T failure or documented incompatibility. |
| 2026-09-25 | Isolate simulator and policy dependencies behind a loopback HTTP worker. | Pinned RoboCasa and GR00T require incompatible Tianshou versions. The worker verifies checkpoint identity and returns learned action chunks only. |
| 2026-09-25 | Require both nominal and naturally encountered intermediate entry conditions for every fixed skill. | Each condition needs at least 8/10 valid trials. This prevents a nominal-only aggregate from hiding unreliable handoffs. |
| 2026-09-25 | Add a matched-continuation relevance gate. | Qualification cannot pass from skill and full-task rates alone; retained traces must show a naturally reached state where supervision choices can change the outcome. No artificial disturbance is allowed. |
| 2026-09-25 | Keep development, diagnostic, and official model artifacts distinct. | Official runs require a frozen release manifest bound to the qualified checkpoint, contract hashes, trace evidence, and evaluation seeds. |
| 2026-09-25 | Defer exact LLM identifiers and GPU instance selection. | Both must be recorded before evaluation and then remain fixed. No suitable Prime Intellect worker is provisioned yet. |
| 2026-09-27 | Use an RTX 6000 Ada and Opus 5.5 only for the first live development pass. | The two prerequisite GR00T episodes and one Opus episode completed under an independently verified two-hour termination watchdog. The pod was terminated early; $0.93 of team compute credit was billed. This is a harness check, not a model comparison. |
| 2026-09-27 | Keep the CerealAndBowl qualification gate pending after three unsuccessful episodes. | Both ordinary and Opus runs moved cereal and bowl onto the counter at least once, but did not close the cabinet. The first diagnostic supervisor never changed from its open-cabinet prompt because the source `cabinet_open` predicate stayed false, even though object transfer proved possible in other episodes. Revise and predeclare its transition rule before further counted trials; one seed per condition is insufficient. |
| 2026-10-01 | Raise the maximum observation interval from 100 to 400 control steps and add four evenly spaced interval keyframes per camera to each observation. | Supports the intervention-judgement direction: a supervisor can trust the policy for up to 20 s of robot time without being blind to what happened in between. Keyframes are public camera images only, sampled strictly inside the executed interval; none are sent on the first call or after a rejected decision. Model observation schema advances to 3, task-config schema to 3, and system prompt to version 3. The privileged ordinary-policy diagnostic keeps its previous 100-step success-check granularity. Earlier development episodes used the old contract and are not comparable. |
| 2026-10-01 | Use each task's native RoboCasa language instruction, verbatim, as the goal for the intervention-judgement benchmark. | Benchmark task configs set `goal: null` with `goal_source: native_instruction`; the runner reads the instruction from the environment after the scene reset and records it as `goal` in `result.json`. CerealAndBowl keeps its audited authored goal. Checkers are never edited. `docs/task_catalog.md` lists each instruction template and where its checker differs, for example unstated gripper-release conjuncts. Instruction texts are not yet verified against the real simulator. |
| 2026-10-01 | Score every non-CerealAndBowl task with the official upstream `_check_success`, read unmodified. | `RoboCasaEnvironment.evaluate()` returns that value as `success` for any task. Per-task predicates in `tasks/predicates.py` are logged beside it for diagnostics and attribution only and may not redefine `success`. The declaration rule is unchanged: success still needs `complete` while the checker is true. CerealAndBowl keeps its asserted three-predicate decomposition. |
| 2026-10-01 | Separate the scene seed (`env.reset`) from the policy seed (`policy.reset_episode`). | Before this change the runner seeded the policy worker's sampling stream with the scene seed, so repeated runs on one scene were near-identical. An episode is now `(task, scene_seed, policy_seed)`; the policy seed defaults to the scene seed, so legacy commands behave as before. `configs/splits.json` adds disjoint `screening_policy_seeds` (set A, 0–4) and `reference_policy_seeds` (set B, 5–9). Group labels come from set A and reference rates from set B, which avoids selection bias. Manifests and results record both seeds. |
| 2026-10-01 | Add the privileged diagnostics `diagnostic_reference` (plain policy with the native instruction, checker polled every 100 steps), `diagnostic_retry` (re-issues the native instruction after 300 steps without success) and `diagnostic_sequencer` (composites only; predeclared step prompts driven by subgoal predicates). Add the public baselines `baseline_always_defer` and `baseline_reissue` (same prompt every 100 steps). | The diagnostics read simulator truth. They only label seeds and supply the reference, and the scorecard never lists them as systems. The baselines read only public observation fields and are scored like models. An LLM that cannot beat both baselines is not showing judgement. |
| 2026-10-01 | Give each benchmark task config only one public card, `native_instruction`. Keep composite step prompts privileged in `tasks.predicates.SEQUENCES`. | The step prompts are a subtask decomposition derived from upstream annotations, which AGENTS.md forbids exposing to a model adapter. They would also confound the intervention judgement being measured. The spec's "step prompt rates where measured" cards are therefore not published. Re-adding them later would be a contract change. |
| 2026-10-01 | Define a 16-task candidate pool in `configs/tasks/`: 10 `atomic_seen` and 6 `composite_seen` RoboCasa365 tasks. | Selection criteria and per-task source findings are in `docs/task_catalog.md`. Composite-unseen tasks are excluded because the plain policy is near zero on them, so they have no leave-alone seeds. Screening decides which tasks qualify; the first release keeps 10. No task is yet screened or GPU-verified. |
| 2026-10-01 | Relax the CerealAndBowl `video_record_interval` check from exactly 1 to any positive integer, and let `screen`/`baseline` override it with `--video-record-interval`. | Recording cadence only changes which frames are stored. Keyframes shown to the model are sampled independently. Each manifest records the interval actually used, and the override is left out of the contract hash. |
| 2026-10-01 | Name episode directories `seed-<scene>-p<policy>-<timestamp>`. Make `summarize` seed lists and paired comparisons `[scene, policy]` pairs. | Several policy seeds per scene would otherwise collapse onto one key. Legacy manifests without `policy_seed` pair the scene seed with itself. Tools that parsed `seed-<N>-<timestamp>` names or flat seed lists must be updated. |
| 2026-10-01 | Bind screening, baseline and LLM runs to one benchmark contract (payload schema 3) covering the whole `configs/tasks` pool. Add the new modules to the implementation hashes. | Each `screen`, `baseline`, `freeze-benchmark` and benchmark `run` payload holds every pool config, the splits, policy identity, source revisions, system prompt, model-call token limit, and SHA-256 hashes of the contract files. The new files are `tasks/predicates.py`, `diagnostics.py`, `baselines.py`, `scorecard.py`, `screening.py` and `feasibility.py`. A command running any subset of tasks therefore produces the same hash, which the scorecard filters on. Each passed config must equal its pool entry. Editing any pool config, the splits, or a contract file changes the hash for every task: do it before the set-B reference runs, or rerun them. All contract hashes change, including the legacy CerealAndBowl ones, so earlier episodes and releases do not match. `run --release` tells release formats apart by the `tasks` key that `freeze-benchmark` writes. A legacy release keeps the per-task CerealAndBowl contract and rejects `--policy-seeds`. A benchmark release requires `--policy-seeds` from its `reference_policy_seeds`, its selected scene seeds, a listed task, and a listed model. `feasibility` now rejects tasks other than CerealAndBowl; `screen` covers native-goal tasks. |
| 2026-10-01 | Predeclared before screening: `diagnostic_retry` checks success every 100 steps (was 50) and counts as rescue evidence only if it actually re-prompted. | The retry diagnostic now uses the reference's success-check granularity. `label-seeds` counts a `diagnostic_retry` episode as a rescue success only when `result["prompt_submissions"] >= 2`. A retry episode that succeeds without re-prompting is a usable trial but not a success, because it shows only that the plain policy succeeded. The rule is fixed before any screening episode exists. |
| 2026-10-01 | The native card's prompt is the literal template `"{goal}"`, and the card reports set-A screening performance. | `Runner.observation()` replaces a card prompt that is exactly `"{goal}"` with the episode's goal. This happens only in the observation copy, and only for the goal, which is already public. Card description: "Card for the task's native RoboCasa instruction (the goal text)". `publish-cards` writes `screening.native_card_performance` into each screened config and sets `status: screened`: plain-policy success, trials, a Wilson 95% interval and `policy_seeds: "screening set A"` over all screened scene seeds. That is a per-task rate, not a per-seed estimate. Unscreened tasks stay untested/null. Configs are hashed, so cards are published before the set-B reference runs. This changes the contract hash. |
| 2026-10-01 | Remove `scorecard.py` and `screening.py` from the contract hash; record them under `release["analysis_sha256"]`. Same GPU type, code, configs and splits from set B to final runs. | These modules only analyse episodes, so fixing a scorecard bug no longer invalidates set-B and model runs. `freeze-benchmark` records their SHA-256 for audit. Supervisor and baseline parameters come only from module defaults in hashed modules (`diagnostics.py`, `baselines.py`, `feasibility.py`); `screen` and `baseline` pass no parameters. The policy worker identity, including the GPU name, stays in the hash. Set-B reference, baseline and LLM runs must therefore use the same GPU type, code, configs and splits as the freeze, or their episodes stop matching the release. |
| 2026-10-01 | `llm_development` is not a scored system. | The scorecard excludes it and counts it as `excluded_development`. The scored systems are `llm`, `baseline_always_defer` and `baseline_reissue`. Development runs are not bound to a release. |
| 2026-10-01 | Harm and rescue use paired clusters only. | Point estimates and the seed-clustered bootstrap use only (task, scene seed) clusters with at least one usable system episode and at least one usable set-B reference episode. Each system and group reports `unpaired_clusters`. Per-group success rates still count all usable episodes. |
| 2026-10-01 | Predeclared before screening: if more than 10 tasks qualify, the release keeps the top 10. | Ranking: `min(len(selected leave_alone), len(selected needs_help))` descending, then total selected seeds descending, then task name ascending (`freeze_release(max_tasks=10)`). This rule is fixed before screening results exist, so no task can be picked by its outcomes. |
| 2026-10-01 | LLM and baseline runs use one policy seed per scene by default: the first `reference_policy_seed` (5). | This matches the cost estimate in spec section 8. More set-B policy seeds are allowed and are paired the same way. With one episode per scene, small differences are not significant, so overlapping intervals are not ranked. |
| 2026-10-01 | Operational safeguards for GPU runs. | `screen`, `baseline` and `run` accept `--skip-existing`, which skips a (task, scene seed, policy seed, kind, agent model) that already has a non-infrastructure-error result under `--output` with the current contract hash (episodes under other hashes are re-run and kept on disk). A task with 3 consecutive infrastructure errors is abandoned and the grid continues; two tasks abandoned back to back stop the grid (likely a dead worker). Written episodes are kept and the exit status is nonzero. `run` accepts `--video-record-interval`, which is not hashed. Contract payloads are written to `contract-<hash>.json`. `screen --scenes-from groups.json` limits retry/sequencer screening to low-success scenes. `freeze-benchmark --reference-root` requires a usable set-B `diagnostic_reference` episode under the frozen hash for every selected scene and reference policy seed. `baseline --release` applies the `run --release` task and seed checks. None of these changes what an episode does. |
| 2026-10-02 | Describe proprioception to the model, carry it on keyframes, and report both clocks. | The system prompt (version 5) states each proprioception field's frame, units, quaternion order, that a quaternion and its negation are the same orientation (the first GPU run showed sign flips between keyframes), and the gripper range, taken from the pinned robosuite Panda gripper model (finger slide joints 0 to 0.04 m; checked against the first GPU reading of about 0.0206 m, half open at step 0). Each interval keyframe now also carries the robot's proprioception at its step (observation schema 4). This is body state a real robot's encoders and odometry report at timestamped samples, so it needs no perception or inference. It adds a few dozen numbers per keyframe and is not derived state. Base position is exact in simulation but would drift on real odometry; these tasks barely move the base. `result.json` already held `simulated_seconds`, `wall_seconds`, `model_seconds`, and `policy_seconds`; the scorecard and `summarize` now aggregate them. The contract hash changes; no LLM episodes exist yet. |
| 2026-10-02 | Enforce the reply format at the API and recover an unambiguous decision from a narrated reply. | The adapter parsed the whole reply text as one JSON value, so any prose before or after the JSON became a rejected, charged decision that advanced no physics; this was reproduced against the old adapter with a valid `run_policy` object after one sentence of reasoning, and it cost 11 of 72 calls (15%) in the October 2 Sonnet 5.5 stage 1 runs (`docs/stage1_remote_results.md`), each a reply with prose or a code fence around the JSON. Anthropic requests now also carry `output_config.format`, a flat JSON schema for the two operations, so the text block cannot hold prose. If other text still appears, the decision is accepted only when `stop_reason` is `end_turn` and exactly one distinct object with a string `op` is present; conflicting objects (for example a considered-but-rejected `complete`), truncated or refused replies, and prose without a decision stay rejected and charged. Every reply records `parse` as `strict`, `extracted`, or `unparsed` beside the raw text. The system prompt (version 5), budgets, and `validate_decision` are unchanged, so ranges, field combinations, and prompt length are still checked by the harness. Pathologically nested text is now a rejected reply instead of an infrastructure error. This changes the evaluation contract for every Anthropic-provider model; `json_http` servers must still return a parsed decision. Earlier development runs used strict parsing, remain preserved unchanged, and are not comparable to runs under this contract. Live acceptance of the schema by the pinned models has not been tested: a rejected request would end the first decision as an infrastructure error, so probe once before any paid GPU run. |
| 2026-10-02 | Retry transient model-API failures inside one decision, and count rejected replies in `result.json`. | A single overloaded, rate-limited, timed-out, or dropped model request used to raise out of `decide()` and end the whole episode as an infrastructure error. A model call changes no simulator or policy state because physics is paused, so `HTTPAgent` now retries HTTP 408, 429, 500, 502, 503, 504 and 529, timeouts, and connection errors up to three times after 5, 20 and 60 s, honouring `retry-after` up to 120 s. Requests the provider rejects (other 4xx, such as a schema it refuses) are not retried. A retry is not a decision and the model never sees it; each one is logged under `retries` in `model_api_traces.jsonl`, and the wait counts toward `model_seconds` and wall time, not simulated time. A timed-out request may still be billed by the provider. Policy-worker calls are still never retried. `result.json` now carries `rejected_decisions` and `reply_parse` (counts of `strict`, `extracted`, `unparsed`), which settles the first pending decision in `docs/stage1_remote_results.md`. Contract hashes change because `agents.py` and `runner.py` are hashed. |
